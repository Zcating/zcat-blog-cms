# 后端地址是一个概念、两种表示

仓库里存在两个"后端地址"变量，各自独立配置：`BACKEND_API_URL` 在服务端请求时读取（因此可以是容器内网地址），`VITE_API_URL` 在构建期内联进产物（因此必须是浏览器可解析的形态）。ADR-0003 删除了 `/api/bff/*` 之后，前端已全面走服务端边界，但博客仍保留一条客户端直连后端的路径（访客访问计数），而它的 `VITE_API_URL` 已腐烂成 `/api/bff`——该表面在代码中完全不存在，请求 404 且被静默吞掉。根因不是笔误，而是两个变量**没有任何机制保证一致**。

## 决策

- 领域上承认「后端地址」只有**一个**概念，它有**两种表示**：服务端表示与客户端表示。二者必须一致，并由测试钉住。
- 客户端表示统一为 `/api` 挂载前缀，与服务端表示的 `/api` 后缀对齐。
- 每个新增的后端调用方必须明确声明它使用哪一种表示；`VITE_API_URL` 当前唯一的消费者是访问计数。
- 访问计数**留在客户端**（它读取 `document.referrer`、`navigator.userAgent`，依赖浏览器指纹库），不改为服务端转发。

## 理由

不合并为单一变量的原因是硬约束：浏览器端 `fetch` 只能在构建期拿到值，服务端变量帮不上忙。因此短期内两份表示必须并存，可靠性只能来自"把它们当成同一个概念，并让测试强制一致"。曾考虑把访问计数改为 server function，但那会改变这条请求的信任边界（服务端代发），且与 ADR-0003 记录的"该调用留在客户端"相冲突。

## 后果

未来若再出现"新增运行时变量却没写进部署配置"，其失效模式是静默的——见 ADR-0007。
