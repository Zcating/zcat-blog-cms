# 后端地址是一个概念、两种表示

仓库里存在两个"后端地址"变量，各自独立配置：`BACKEND_API_URL` 在服务端请求时读取（因此可以是容器内网地址），`VITE_API_URL` 在构建期内联进产物（因此必须是浏览器可解析的形态）。ADR-0003 删除了 `/api/bff/*` 之后，前端已全面走服务端边界，但博客仍保留一条客户端直连后端的路径（访客访问计数），而它的 `VITE_API_URL` 已腐烂成 `/api/bff`——该表面在代码中完全不存在，请求 404 且被静默吞掉。根因不是笔误，而是两个变量**没有任何机制保证一致**。

## 决策

- 领域上承认「后端地址」只有**一个**概念，它有**两种表示**：服务端表示与客户端表示。二者必须一致，并由测试钉住。
- 客户端表示统一为 `/api` 挂载前缀，与服务端表示的 `/api` 后缀对齐。
- 每个新增的后端调用方必须明确声明它使用哪一种表示。
- 访问计数的**数据采集留在客户端**（它读取 `document.referrer`、`navigator.userAgent`，依赖浏览器指纹库，这些无法搬到服务端）；但**传输走同源转发**，浏览器 POST 到博客自己的 `/api/blog/visitor`，由 `server/visitor` 的 `forwardVisitRequest` 转发到 `BACKEND_API_URL`。
- 转发时 `data-hash`、`x-forwarded-for`、`x-real-ip` 必须原样带往后端，使后端能取到真实访客 IP 并校验签名。

## 变更记录

- **2026-10-07 修订**：原决策为"访问计数不改为服务端转发"。实际执行 `ef21abd` 时发现该约束与本 ADR 的另一条决策直接冲突：客户端表示被规定为 `/api` 挂载，而访问计数却按 `VITE_API_URL` 直连后端——即客户端表示与 ADR-0003 删除的 `/api/bff` 一样，在代码中并不存在，实际请求 404 且被静默吞掉。这正是本 ADR 开头要消灭的失效模式。因此改为经同源 `/api` 转发，`VITE_API_URL` 随之失去全部运行时消费者。
- **待办**：`VITE_API_URL` 现已是死变量（仅剩类型声明、`Dockerfile.blog` 的 ARG、`package.json` 的 e2e 构建注入与本 ADR 文字）。删除前需同步 `apps/blog/app/vite-env.d.ts`、`Dockerfile.blog`、`test:e2e` 脚本与各 `.env*`，并确认部署侧不再注入该变量。

## 理由

不合并为单一变量的原因是硬约束：浏览器端 `fetch` 只能在构建期拿到值，服务端变量帮不上忙。因此短期内两份表示必须并存，可靠性只能来自"把它们当成同一个概念，并让测试强制一致"。

同源转发并不改变"该调用留在客户端"这一 ADR-0003 结论：指纹采集与 UA 解析仍在浏览器内完成，服务端只做一次不解析载荷的透明转发（`forwardVisitRequest` 只透传 `data-hash` / `x-forwarded-for` / `x-real-ip`，响应原样返回，载荷校验仍由后端单点定义）。代价是请求的信任边界从"浏览器直达后端"变为"经博客服务端代发"；收益是后端首次能拿到真实访客 IP，且客户端表示与本 ADR 的规定一致。

## 后果

未来若再出现"新增运行时变量却没写进部署配置"，其失效模式是静默的——见 ADR-0007。`app/server/backend-url-contract.test.ts` 必须以**真实生产代码**驱动两端（客户端走 `StatisticsApi.uploadVisitRecord`，服务端走 `forwardVisitRequest`）来钉住一致性；写成硬编码字面量的自我比对无法发现任一端漂移。
