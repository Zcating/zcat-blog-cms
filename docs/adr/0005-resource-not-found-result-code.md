# 资源不存在用专用响应码 ERR0007 表达

本领域此前**没有**「资源不存在」这一概念的表达方式，后端用两种互不相容的方式临时表达它：文章不存在时返回 `ERR0003`（术语表定义为「数据库操作错误」），相册不存在时返回 `200` 加 `data: null`。后果是同一个响应码在两种语境下含义不同，而 `null` 与「响应畸形」无法区分。客户端因此不得不**匹配中文字符串**（如 `文章不存在`）来区分「不存在」与「故障」——后端一改文案，缺失资源就静默退回 500，爬虫收到 5xx，监控出现幽灵 500。

## 决策

- 新增 `ERR0007` = 资源不存在，同时登记进 `CODE_ENUMS` 与 `ResultCode`（`createResult` 按前者校验，未登记的码会抛 `Invalid code`）。文章不存在与相册不存在都以 `ERR0007` 报告，且不带 `data`。
- **后端不产出 404。** 它在 HTTP 200 的信封里报告 `ERR0007`：`middleware/error-handler.ts` 对 ZodError、HTTPException 与未捕获异常一视同仁地把响应码写进信封并返回 200，这条既有约定不动。
- **应用层**负责把 `ERR0007` 变成 404：应用的 HTTP 传输层按响应码分类，路由在缺失时 `throw notFound()`，根边界 `apps/blog/app/routes/__root.tsx` 由 `routeError.isNotFound` 算出 404。后端一半已实现并有测试固定，应用一半待做。
- `ERR0003` 恢复为纯「数据库操作错误」，不再兼表资源缺失。
- 相册详情的 `200 + data: null` 改为 `ERR0007`；`null` 仅保留在后端 HTTP 传输层内部用于表达"无数据"，不再出现在成功信封里。
- 客户端**禁止**通过匹配错误文案判断语义，一律按响应码判断。
- `middleware/auth.ts` 不动：被拒绝的 token 仍是 `ERR0002`。「不被允许」与「不存在」是两件事。

## 理由

曾考虑让 HTTP 状态码承载「不存在」（错误体仍用 `ERR0003`），改动面更小，因为根边界已经会读 `error.status`。但那样同一个 `ERR0003` 在 500 和 404 下含义不同，错误码不再是权威，与本仓库"响应码是权威词汇"的既有约定冲突。也考虑过让「缺失」成为成功的一种（`200` 加可辨识标记），概念上最干净，但与"成功信封的 `data` 必须是对象"这一前端 schema 约定冲突面最大。

**已否决：在后端 `middleware/error-handler.ts` 里把 `ERR0007` 映射为 404。** 否决依据是实测而非偏好：既然每类业务错误都已在 200 的信封里带上响应码，只给 `ERR0007` 一个 404 会让它**更不权威**——它成了唯一需要靠状态码才被识别的码，与"按码判断"的约定相反；而把两个公开端点从 200 翻成 404，是比本决策所设想的向后兼容更大的客户端可见破坏。后端 HTTP 传输层本就不统一（`@hono/zod-validator` 对畸形 query 直接返回裸 400 与非信封 body），再叠一层状态码例外只会增加而不是减少推断。

新增响应码是**向后兼容**的，破坏面已逐项实测：文章列表是纯增量（多一个 `total`，该值本来就在算然后丢弃）；相册列表的 `total` 含义改变并新增 `totalPages`（旧值最多等于 `pageSize`，无法支撑任何正确行为，因此不可能有东西依赖它）；文章详情的响应码从 `ERR0003` 变为 `ERR0007`，在尚未学会该码的客户端上降级为 `UnknownError`，而 message 未变，因此 blog 现有的字符串匹配边界在过渡期仍能渲染。

## 后果

`ERR0007` 一旦被客户端依赖便不可移除。错误文案从此只是展示内容，不再是可依赖的接口。

以下两处是**有意留下的边界**，不是疏漏：`ERR0007` 也覆盖「这个 id 根本指不到任何行」的情形，因为 `safeNumber` 把非数字 id 变成 0，查询随之落空，`/article/abc` 因此报缺失；分页校验仍接受 `pageSize=0`，由 `createPaginateResult` 处理而非拒绝，因为拒绝它会把 200 变成 400。
