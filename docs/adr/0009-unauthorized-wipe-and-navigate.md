# 认证失效时清空私有缓存并导航到登录页

CMS 的锁定要求是：401 与退出登录都必须清空 TanStack Query 的私有缓存，使一个会话无法渲染另一个会话的缓存私有数据。该要求曾被误报为已闭环——测试全绿而生产从未生效，因为后端的错误信封不带 `data` 键而前端的 schema 要求它，导致每个真实认证失败都被误分类，`isUnauthorizedError` 的 `_tag === 'LoginError'` 从未命中。修复后响应式路径已生效，但仅止于清缓存。

## 决策

- 服务器函数返回 401 时：**清空私有缓存并导航到登录页**。
- 这与已有的主动式路径一致——`_cms` 守卫在会话失效时本就重定向到登录页。
- `QueryCache` 与 `MutationCache` 两侧走同一个清空函数，清空后不保留任何私有条目。

## 理由

在单 JWT、永不过期、由后端 whitelist 管理的令牌模型下，401 意味着会话**确实**已失效，不存在需要自动恢复的瞬时 401。因此让用户停留在一个渲染着其已无权限查看的数据的页面上，是三种可选行为里最差的一种。而当前只清缓存不导航，正是这一半无法在浏览器层证明的原因：挂载中的 `useSuspenseQuery` 在缓存被清后会孤立并继续渲染旧数据。导航会卸载该视图，从而消除这一整类问题。

曾考虑"清缓存 + 整页刷新"，但那会丢失所有未提交输入与滚动位置，对一个可预测导航即可解决的问题过于粗暴。根本修复（让缓存清理本身通知观察者，例如改用会通知的移除 API 或升级 query-core）是值得做的**跟进**，但不应替代本决策——本决策与其向后兼容。

## 后果

任何位置的 401 都会把用户可见地送回登录页。这是有意的：会话已死，继续停留在原页面并不比重新登录更安全。Query 侧的观察者通知缺口仍存在，只是被导航掩盖；跟进项是让缓存清理对挂载视图生效。
