# 分页结果统一为 data / total / totalPages / page / pageSize

两个分页端点给出两套互不兼容且**各自都不完整**的分页词汇：文章列表返回真实的 `totalPages` 但没有 `total`；相册列表返回 `total` 但**没有** `totalPages`，而那个 `total` 实际是 `galleries.length`，即**当前页的条目数**而非总条数。相册端点因此无法计算页数，页面完全不能渲染分页控件，且一旦可用相册超过一页就会静默丢失且无从访问——这是一个尚未发作的用户可见缺陷，而非仅仅是不够整洁。

## 决策

- 所有分页查询返回统一形状：`data`（当前页条目）、`total`（**总**条数）、`totalPages`（**总**页数）、`page`（当前页码）、`pageSize`（每页条目数）。
- `total` 必须来自真实的 `count` 查询，不得由当前页数组长度推导。
- 客户端按需选用字段，不再依赖某个端点特有的形状。

## 理由

曾考虑统一为 `{ data, total, page, pageSize }`（字段最少，页数由客户端算），但那会删除文章端点现有的 `totalPages`，属破坏性变更。也考虑过统一为 `{ data, totalPages, page, pageSize }`（保持文章端点零破坏），但客户端因此拿不到总条数，依赖"共 N 条"的界面仍需额外请求。选择完整形状是**纯增量**：文章端点多一个字段，相册端点修正一个本就无用的字段含义——旧值不可能被任何东西依赖，因为它无法支撑任何正确行为。

## 后果

`totalPages` 与 `total` 并存看起来冗余，可能会有人"简化"掉其中一个。**不要**：`total` 回答"有多少条"，`totalPages` 回答"有多少页"，两者在页大小会变化时不等价。
