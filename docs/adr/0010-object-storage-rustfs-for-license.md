# 对象存储服务端由 MinIO 换成 RustFS，理由是许可证而非性能

MinIO 的**服务端**采用 AGPL-3.0，本项目不接受；RustFS 服务端采用 Apache-2.0。需要说明的是，`minio` 这个 npm 客户端 SDK 本身是 Apache-2.0，与许可证问题无关，因此**客户端不动**——被替换的只有服务端。这条区分决定了本次改动的性质：不是"换一个对象存储客户端"，而是"换一个服务端进程"。

需要一并记录的是：本项目的对象存储用量极小。后端只发起**两个**真正的 S3 调用——60 秒有效的预签名 PUT（供浏览器直传）与删除对象；**读取完全不经过 S3**，而是由代码拼出的公开地址加匿名 GET。桶与公开读权限从未由代码创建，一直是人工施加的状态。

## 决策

- 服务端换成 `rustfs/rustfs:1.0.0`，**固定版本**。spike 验证与上线必须是同一个构建产物，浮动 tag 会让今天取得的证据不再对应将要部署的东西。
- 保留 `minio` npm SDK 作为通用 S3 客户端。它 Apache-2.0，且已是既定依赖；换掉它不解决许可证问题。
- 环境变量与代码标识符一律改用供应商中立名：`OSS_*` 与 `oss*`。**不是** `RUSTFS_*`——契约里的供应商名会让下一次换型成本最高。
- 凭据**合并为一对** `OSS_ACCESS_KEY` / `OSS_SECRET_KEY`，服务端与客户端共用；由 compose 把这对中性名映射为服务端认识的 `RUSTFS_*`。
- 桶与公开读策略由后端容器启动时的一次性幂等脚本创建，复用已有的 S3 SDK，**不引入任何额外镜像**。
- 去掉对象存储服务的健康检查，`depends_on` 降为 `service_started`，改由引导脚本带退避重试自行等待。
- Web 控制台保留，但只绑定 `127.0.0.1`。

## 理由

**许可证是本次唯一不可谈判的一维。** 其余各轴——性能、内存占用、上游方向、运维复杂度——都是可权衡的，而许可证不是：它不随时间变化，且一旦违反，纠正成本是把受影响代码从产物中清除。因此选择的标准首先是"能否满足许可证约束"，其次才是别的。

在此前提下，RustFS 的成熟度信号是**混合的**，我们明确接受其中不利的一部分。项目尚新（1.0.0 是 2026 年 1 月的 GA），其与 MinIO 磁盘格式互操作被官方标为 Preview 且门控在默认构建之外；README 明确写明单节点单盘只作为独立本地路径支持，而这正是本项目的部署形态。这些都是真实代价，记录在此是为了让下一个读者知道它们是被接受的，而不是被忽略的。

曾考虑并否决的替代方案：

- **SeaweedFS**（同为 Apache-2.0、且成熟度更高）——许可证同样满足，因此在许可证这一维上并不更优。需要重新走一遍选型调研才值得换。
- **改用托管 S3**——许可证问题彻底消失，也没有自托管运维。但引入费用与出网流量，且照片 URL 的归属域名会变。
- **彻底去掉对象存储这一层**（图片存磁盘、反向代理静态服务）——本项目只有 31 张照片、约 1.3M，这个方案在资源上最省。但它要改 `photo.url` 契约与整条上传流程，范围**大于**换服务端，因此作为后续可能方向记录，不在本次。

**两条命名与结构决策的理由值得单列。** 其一是把供应商名从契约里拿掉：名字比供应商活得久，本次正是因为许可证而更换 MinIO，下一次很可能同样原因再换一次，所以把 `MINIO_*` 改名不是洁癖而是让契约不重复说谎——`CONTEXT.md` 早已把 `OSS` 定为本项目对该概念的中性用词，此前不一致的只是变量名。其二是把两段式凭据合并为一对：MinIO 的服务端与客户端使用两个不同的名字，但实测确认那是**同一对全权凭据的两端**，保留这种拆分会让人误以为是两样东西。

引导脚本挂在后端启动而非部署脚本，是因为要解决的问题是"新的卷起来之后没有任何代码会报错、系统却已经坏了"；只把它写在文档里或接在部署流程末尾，都存在绕过路径而不自愈的缺口。它的幂等性使得每次启动都执行的代价可以接受。

## 后果

- **契约与实现之间多了一层间接。** 环境变量叫 `OSS_*`，服务端是 RustFS，这个映射只存在于 compose。一处需要知道的额外事实。
- **凭据合并后，控制台等价于后端凭据。** 合并没有提升权限（本来就是同一对全权凭据），但它使得"暴露一个接受该凭据的管理界面"与"暴露后端自己的凭据"等价，因此控制台只绑 `127.0.0.1`。
- **RustFS 不支持桶 ACL 授权**（官方兼容性矩阵标为 intentionally unsupported），公开读只能用桶策略表达。引导脚本因此必须走 `PutBucketPolicy`，用 ACL 会失败——这属于预期，不是缺陷。
- **启动时序的责任转移到引导脚本。** 去掉健康检查意味着"存储是否就绪"由引导脚本的退避重试负责，失败信息出现在它的日志里，而不是 compose 的服务健康状态里。
- **不得调用桶 ACL**，也**不得在签发预签名 PUT 时带上 `ContentMD5` 或 `ContentLength`**——后者是 RustFS 侧已记录的 `SignatureDoesNotMatch` 来源；本项目现有代码不带，故天然避开。
- **本记录在 spike 通过前保持 `proposed`。** 上述兼容性判断目前来自官方文档与源码阅读，尚未在运行的系统上验证；上线前还须复核官方镜像页的生产就绪声明（撰写本记录时该页面未能取得）。
